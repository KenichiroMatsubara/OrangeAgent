# Keep the sign-ins of a browser every run operates

Every run the Account starts, in Operator Chat or as an unattended Automation, may operate a real browser from Cloudflare Browser Run: it opens pages, reads them with each control numbered, clicks, types, chooses, and presses keys, through the same six `browser.*` tools and the same handlers. It is off until a person turns it on on the ブラウザ screen, since a browser call acts on a site at once and a saved sign-in acts as the person who made it, and an Automation's Tool Grant names the tools it may use. A person signs in to a site once, in Browser Run's Live View of a tab FlareChat opened; FlareChat then keeps what that browser holds of the sign-in (its cookies and the site's localStorage) under the Account's envelope encryption, puts every saved sign-in back into each run's browser before its first page opens, and at the run's end writes back what the sites renewed.

We chose to keep sign-ins rather than have each run ask a person to sign in through a Live View while it waits, because an Automation runs with nobody at it, and a run that must wait for a person is no longer the same engine whichever entrance started it. The cost is that FlareChat now holds credentials for other people's sites: a saved sign-in acts as the person who made it until the site expires it or it is deleted, and nothing in FlareChat can see which sites a cookie also opens.

A browser call acts on the site the moment it is called, as an MCP Server's tool does, so it is bound only to an unattended run: it cannot be held as a Planned Write for an approval, which would come after the click it was meant to gate, and a read-only run must reach no third party. The browser is spoken to over the Chrome DevTools Protocol directly through the Worker's `browser` binding rather than through `@cloudflare/puppeteer`, so the Worker needs no Node.js compatibility and no browser library.
