# Keep Tasks in Google Tasks

An Account's Tasks are tasks of Google Tasks, in the Google account of its Automation Inbox, and FlareChat keeps no copy of them. A run reaches them through three tools that say only what Google Tasks says — `tasks.search`, `tasks.create`, `tasks.update` — and everything Google Tasks has no field for is written in a Task's notes, one line each: who it was given to, the Scheduled Event it belongs to, the mail it came from, the key of the work, and that it was cancelled rather than done. Those lines are written and read by a program the Account's タスクの管理 Skill carries, `tasks.py`, which Claude runs in its sandbox and which calls the Task tools from there, rather than by Claude's own reading of the Skill's words.

FlareChat kept Tasks in its own table, with a screen to list them, an assignee column, a status of three values, and a link per Task that let an assignee complete it without signing in (ADR 0185). The Account's owner asked for Tasks to be managed in Google Tasks instead, relying on FlareChat's own database as little as possible. A Task kept in both places would have needed the reconciliation Scheduled Events need, for a record much smaller than an event, so the table goes rather than being mirrored.

We chose to let the product know nothing about a Task beyond what Google Tasks holds, and to leave the rest to the Skills, because what a Task carries is the Account's convention rather than the product's: a different Account may want different lines in the notes, and changes them by rewriting a Skill and its program. The convention is kept by a program because a model that writes and reads a line by instruction drifts — a name spelled another way, a line left out, the same work registered twice — and a program does not; the Worker lets that program call `query_contacts` and the Task tools from Claude's sandbox, which reaches no network, through Anthropic's programmatic tool calling, each call answered and, in an Automation, planned as Claude's own would be. The product still enforces what a Skill must not be able to undo: a run cannot reopen a completed Task, cannot delete one, and a Planned Write that creates one is never applied twice on an unknown outcome, since Google Tasks takes no id from its caller.

## Considered and rejected

- **Google Tasks as the store, with a FlareChat row beside each Task** for the assignee, the event, and the link token. It would have kept the Tasks screen and the Task Link, and with them two places that can disagree about one Task, and a second model of a Task for every run to learn.
- **A Task Link that completes the Google task**, its address signed rather than stored. It keeps ADR 0185's flow, but only the product could write to Google on a stranger's word, for a task whose owner can tick it off in the app they already use. If assignees turn out to need it, it can be built on these tools without a table.
- **Task tools that take the assignee, the event, and a key as arguments**, the Worker writing and reading the notes. It would hold the convention as firmly, but in the product, where an Account could not change it; and the tools would no longer say only what Google Tasks says.
- **Claude writing and reading the lines by the Skill's words alone**, as this decision first had it. Nothing held two runs, or one run and a person, to one spelling, and nothing stopped one piece of work from becoming two Tasks.
- **Mirroring FlareChat's table into Google Tasks both ways.** Google Tasks sends no notification of a change, so the mirror would be a poll, and every field would need a rule for which side wins.

## Consequences

- **Only the people who use the Inbox's Google account see the Tasks in an app.** Google Tasks cannot share a list or assign a task through its API. A Contact learns of a Task from the reminder an Automation sends, and says it is done to a person.
- **An assignee is a name in the notes.** `tasks.py` refuses a name that no Contact or several Contacts have, but a Contact renamed after a Task was written is no longer found by it, and a person who rewrites the notes in Google Tasks can remove the line.
- **Only Claude keeps the convention by program.** A run on a model with no sandbox calls the Task tools itself and writes the lines by the Skill's words, as before.
- **A program outside the product runs the same `tasks.py`** against FlareChat's MCP Server under an Operator Token, handing it the MCP client's call in place of the sandbox's functions.
- **No Tasks without the mailbox.** An Account that has connected no Automation Inbox, and one whose grant predates the Google Tasks scope, has no Task tool until it connects or reconnects. An Access Token, which holds no Google grant, reaches no Task.
- **Every Task Link already sent is dead**, and ADR 0185 is superseded.
- **The move is one way.** The Tasks FlareChat kept are copied into the list named FlareChat by the Worker, since a migration cannot call Google; the `tasks` table stays until every Account's are copied and is dropped by a later migration. Coming back would mean reading Google Tasks into a new table.
