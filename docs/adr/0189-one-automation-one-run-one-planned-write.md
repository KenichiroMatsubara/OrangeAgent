# One Automation, one Run, one Planned Write

> Superseded in part by ADR 0190: every Automation runs at a Trigger Time and names no Contact List; the mail and Morning Triggers are gone.

Every Automation is a Trigger — a mail arriving, the Morning, or a Trigger Time — the Skills it starts with, a Tool Grant, the one Contact List it may reach, an Execution Mode, and a Suppression Window, and all of them are rows of one `automations` table, versioned in one `automation_revisions` table, with their Skills and tools in `automation_skills` and `automation_tools`. Every run, an Operator Chat exchange included, is one row of `runs`, and every write an Automation's run makes is a Planned Write in `planned_writes`, applied as its Execution Mode says: read-only keeps it, approval holds the batch, unattended applies it. The Agent Rule, its Rule Runs, Agent Runs, Rule Effects, Typed Lists, permitted destination lists, and the Schema Rule's remnants are gone, and so is every reader of a tool's earlier name.

We chose this over keeping a mail Automation in `agent_rules` beside `automations` (the first version of this ADR) because two tables for one concept made every reader learn which Trigger lived where, made a mail run plan its writes while a timed run performed them, and gave a mail run destination lists while every other surface used one Contact List. One table makes the Trigger a column the database checks: only a mail Automation has a Selection Policy and a priority, only a timed one a Trigger Time and a next run, and the Morning's is never held for approval, never names a Contact List, and is never suppressed. One way to write means an approval, a resume after a transient failure, and a suppression check work the same whatever started the run. The one exception is `morning.send`, accepted inside the Morning's run, because the Morning Notice must leave that morning.

Migration 0041 rebuilds the tables and copies no automation configuration across. Carrying Agent Rules, their permitted lists, and their revision history into the new shape would have had to invent a Contact List for every rule from Typed Lists of LINE ids and addresses that do not name Contacts, and a guessed reach is worse than none for a product whose safety is whom a run may reach. So every Account loses its Agent Rules, timed Automations, Morning Automation, Prompts, and the history of their runs, keeps its Scheduled Events, Tasks, Contacts, Contact Lists, Morning Entries, deliveries, and Operator Chat conversations with their Runs, and is given its starting Automations again — which reach nobody until the Account names a Contact List on 自動化. The Scheduled Events those rules created no longer name an Owning Automation, and a Task no longer names the write that made it.

## Considered and rejected

**Keep two tables** (`agent_rules` beside `automations`). It moves no production row, but it keeps two run tables, two ways to write, and two ways to bound reach for one concept, which is what this rebuild exists to remove.

**Migrate each Agent Rule into an Automation.** Its selection, Execution Mode, priority, and Skills carry over cleanly; its reach does not, because a permitted LINE or recipient list is not a Contact List. Rebuilding with no configuration costs each Account one visit to 自動化 and guesses nothing.
