# Let a run answer the calls of the program it starts

A program a run starts — `tasks.py` and the like — calls the run's tools in whatever environment it runs in. In Claude's own sandbox, which reaches no network, it calls them through Anthropic's programmatic tool calling. Anywhere else, the run issues it a Run Token: a bearer token that the MCP Server accepts only while the run that issued it is still thinking, and for fifteen minutes at most, and whose every call is put to that run and answered by it, through the same handlers its model's calls go through. The token's hash names a Durable Object; the run holds a WebSocket to it as long as it thinks, and the MCP Server hands each call to the object, which hands it to the run.

The alternative was a short-lived, scoped token the MCP Server answers on its own, as it answers an Access Token or an Operator Token: a row or a signature naming the run, its tools, and its Google grant, from which the entrance rebuilds what the run could do. We chose to have the run answer instead because the run is the only place that knows everything its calls depend on — an Automation's Planned Writes, which exist only in the run until it ends, its reach, its Suppression Window, an Operator Chat answer's files — and an entrance that rebuilt them would keep one copy of each kind of run to drift from the real one. With the run answering, a call made with the token can do nothing the run itself could not, whichever kind of run it is, and the token stops working when the run ends without being revoked or stored. The cost is a Durable Object class and a socket held for as long as a run that issued a token thinks.

The token passes through the model, which hands it to the program, and so through the AI Connection's provider. We accepted that: FlareChat starts no environment of its own in which to place it directly, and the token is worth no more than the run it came from for a quarter of an hour.
